Where the workflow ends: notes from Microsoft’s Agent Build-a-Thon

November 2, 2026 · 3 min read

Most of my automation work has been about telling a system exactly what to do. At Citizens Bank that meant UiPath workflows that read reports, reconcile counts and flag whatever doesn’t match. At Microsoft’s Agent Build-a-Thon, a hands-on Copilot Studio workshop, the question was different: what does it take to build a system that decides what to do next?

We watched one agent, Pemberton, get built end to end. It’s a daily chief of staff that captures, prioritizes and schedules tasks. The build went one piece at a time: the model, the instructions, knowledge sources, tools, deployment and evaluation. Then we built our own the same way. These are the ideas I’m taking back to my own work.

Not every step should be an agent

The most useful idea of the day was where to draw the line. When a step is predictable, it belongs in a workflow: same input, same steps, same result. An agent earns its place where the next step depends on context, where it has to read a request, choose a tool and decide what happens next. The two aren’t rivals. An agent can call a workflow for the part that has a right answer, and a workflow can call an agent for the part that doesn’t.

I’d already arrived at that split without a name for it. In Forma, my fitness coach, agents handle the conversation, but every calorie target, rate of loss and safety rule comes from deterministic code. In AegisFlow, agents decide insurance claims, and Kafka workflows with idempotent retries make sure each claim is decided exactly once.

Instructions are the interface

Much of an agent’s reliability is set before it runs. The workshop framed instructions as GCSE: the goal, the context the agent works in, the sources it may use, and the expectations for how it behaves and what it returns. Vague instructions get you a demo. Explicit ones, with boundaries and a clear answer for “I don’t know”, get you something people can depend on.

Tools are where an agent meets real systems

An agent that can only talk is a chatbot. Skills, connectors, REST APIs and the Model Context Protocol are what let it read a calendar, file a request or update a record. MCP stood out because I’d used it in AegisFlow, where agents act through MCP tools instead of calling systems directly. It’s the difference between an agent that describes the work and one that does it.

One right answer isn’t a test

The part I’d underline is evaluation. We built evaluation sets and scored responses for groundedness, completeness, relevance, abstention and semantic similarity, with stricter exact or partial matches where there is a single correct answer. An agent isn’t ready because it answered correctly once.

Forma taught me that the hard way. It passed every persona I had written, and then real conversations on its public demo broke it in ways I hadn’t imagined: “3 days in a week” read as a one-week timeline, a torn ACL treated as everyday knee pain. A sweep of 148 checks over real phrasings found 48 deviations. Every one is fixed now, and every one is a regression test.

The old disciplines still apply

What surprised me was how familiar the rest felt. Exception handling, validation, modular design and observability matter as much in an agentic system as they did in the workflows I built at Citizens. The exceptions are just harder to predict, so you need better ways to catch them.

Use a workflow where the answer is known. Use an agent where it isn’t. Test both as if they’ll be wrong.

The future of automation isn’t swapping workflows for agents. It’s knowing where deterministic execution ends, where reasoning adds value, and how to join the two responsibly. Thanks to the Microsoft team for a session spent building, not just watching.
